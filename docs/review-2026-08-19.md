# SubBoost 项目代码审查报告

审查基线：`main` / `2161bc7`。范围覆盖 `local`、`packages/*`、Docker 部署配置及生产依赖。审查以代码可证明的问题为准，不包含个人风格偏好。

## 结论

项目的鉴权、加密字段、Cron 认证、订阅重定向逐跳校验和数据库租约已有较完整的实现与测试。当前最值得优先处理的是：订阅 URL 的 SSRF 校验在 DNS 失败时会失效、公开订阅下载会干扰刷新乐观锁、测活结果存在并发覆盖风险，以及 `js-yaml` 的已知 CPU DoS 漏洞。

## 发现

### P1: DNS 校验失败后回退到未绑定地址的请求，可绕过 SSRF 防护

- 证据：[source-import.ts](../local/src/lib/source-import.ts:109) 在 `lookup()` 报错或无记录时返回 `{ addresses: null }`；[source-import.ts](../local/src/lib/source-import.ts:200) 因此改用 [source-import.ts](../local/src/lib/source-import.ts:161) 的普通 `fetch()`。
- 影响：此时连接使用运行时自己的 DNS 解析结果，既没有私网地址校验，也没有 IP pinning。DNS 校验短暂失败、解析器结果不一致或攻击者控制的域名发生 DNS 重绑定时，管理员导入的订阅 URL 可访问内网或云元数据地址。
- 最小修复：安全模式下 DNS 解析失败应失败关闭，返回可重试的获取错误；若必须保留兼容性，使用第二个受控解析器取得地址后仍通过 `requestPinnedText` 连接。为“`lookup` 失败但运行时能解析到 127.0.0.1/内网 IP”加入回归测试。

### P1: 公开 YAML 下载修改 `updatedAt`，会使进行中的刷新被错误判定为冲突

- 证据：[subscription-service.ts](../local/src/lib/subscription-service.ts:834) 每次公开订阅下载均通过 Prisma `update` 写入 `lastAccessedAt`。`Subscription.updatedAt` 是 Prisma 的 `@updatedAt` 字段，[schema.prisma](../local/prisma/schema.prisma:52)；手动刷新随后以开始时读取的 `updatedAt` 作乐观锁条件，[subscription-service.ts](../local/src/lib/subscription-service.ts:739)。定时刷新也采用同一条件，[auto-update-service.ts](../local/src/lib/auto-update-service.ts:46)。
- 影响：客户端在刷新期间拉取一次订阅配置，就会推进 `updatedAt`，导致刷新最终写入 `updated.count === 0` 并返回 `SUBSCRIPTION_CHANGED`，或被 Cron 当成过期结果跳过。公开订阅本来会被客户端周期拉取，因此该竞态是正常使用路径，而非罕见并发。
- 最小修复：把访问记录从订阅内容版本中分离。最小改动是用不触发 `updatedAt` 的定向 SQL 更新 `lastAccessedAt`，并对该写入做节流；更干净的方案是单独的访问统计表。添加“下载发生在刷新开始和持久化之间，刷新仍成功”的集成测试。

### P1: 手动测活的最终落库可覆盖刷新或编辑刚写入的节点快照

- 证据：[node-health route](../local/app/api/node-health/route.ts:66) 在长时间测活完成后调用 `persistNodeHealthResults`；该函数先读取整条订阅，[subscription-service.ts](../local/src/lib/subscription-service.ts:800)，再无版本条件地整体写回 `encryptedNodes`，[subscription-service.ts](../local/src/lib/subscription-service.ts:812)。相比之下，刷新路径已有 `expectedUpdatedAt` 条件，[subscription-service.ts](../local/src/lib/subscription-service.ts:739)。
- 触发：用户对编辑中的订阅启动测活，测活完成前另一个标签页、手动刷新或 Cron 更新了节点；如果更新发生在测活持久化的读写之间，旧节点列表会被整块写回。
- 影响：新拉取节点、节点删除或编辑结果可能丢失；返回给用户的流仍会显示成功。
- 最小修复：向 `persistNodeHealthResults` 传入并校验版本，或在单一事务中以当前节点快照重新合并，并在节点内容/来源已变化时返回 `409` 而不是覆盖。测试应覆盖测活落库与刷新并发，并断言新节点快照不被旧结果回滚。

### P1: 生产路径使用存在高危 DoS 公告的 `js-yaml@4.3.0`

- 证据：[package.json](../package.json:49) 固定在受影响范围的 `js-yaml`，并在服务端订阅解析 [clash-yaml.ts](../packages/core/src/parser/clash-yaml.ts:166) 使用 `yaml.load()`。`npm audit --omit=dev` 报告 `GHSA-5p4m-2wfm-xmqj`，为 `!!omap` 解析的二次 CPU 消耗，严重性为 high。
- 影响：远端订阅内容或管理员导入的 YAML 在 10 MiB 上限内仍可消耗大量 CPU；自动刷新会反复触发该解析。输入边界是受外部订阅源影响的生产路径。
- 最小修复：升级到公告修复版本（审计结果显示当前 `4.3.0` 受影响），更新锁文件后运行解析、生成和导入相关测试。升级前也应在入口拒绝 `!!omap` 等非业务 YAML tag，作为额外防线。

### P2: 登录与公开订阅限流只存在于单个 Node 进程，且默认部署通常没有客户端 IP 维度

- 证据：[rate-limit.ts](../local/src/lib/rate-limit.ts:14) 使用模块内 `Map`；进程重启和横向扩容都会重置计数。[rate-limit.ts](../local/src/lib/rate-limit.ts:79) 仅在 `TRUST_PROXY_HEADERS=true` 时读取转发 IP，而示例配置默认 `false`，[local.env.example](../local/local.env.example:11)。路由把它用于登录和公开订阅下载：[login route](../local/app/api/auth/login/route.ts:17)、[config route](../local/app/api/subscriptions/[id]/config.yaml/route.ts:17)。
- 影响：多副本或重启时限制可被线性放大；默认反向代理配置下只有用户名桶和 token 桶，无法抑制按客户端来源的滥用。达到 10,000 桶时，现有窗口中的桶也会被主动驱逐。[rate-limit.ts](../local/src/lib/rate-limit.ts:26)
- 最小修复：在生产入口（反向代理/WAF）实现 IP 限流，或将桶放入 PostgreSQL/Redis 并用原子操作计数。保持 `TRUST_PROXY_HEADERS` 的显式信任开关，不要无条件相信可伪造的头。

### P2: 规则目录和规则列表的远程请求没有超时或大小上限

- 证据：[rules/index.ts](../packages/server-core/src/rules/index.ts:101) 与 [rules/index.ts](../packages/server-core/src/rules/index.ts:463) 直接使用 `fetch`，未提供 `AbortSignal`、响应体上限或读取超时。它们由公开 API 路由调用：[search route](../local/app/api/rules/search/route.ts:15)、[CN candidates route](../local/app/api/rules/cn-candidates/route.ts:14)。
- 影响：GitHub 或规则源连接挂起、响应异常变大时，请求会长期占住连接与内存；同一进程的 `indexInflight`/`discoveryInflight` 还会让后续相同查询一起等待。
- 最小修复：复用订阅拉取已具备的“超时 + 流式字节限制”模式，至少为规则索引和 `.list` 下载增加 `AbortSignal.timeout()` 与合理上限，并测覆盖超时、过大响应和 inflight 清理。

### P2: 自动刷新在单个租约持有者中逐订阅串行执行，容量与最小 6 分钟调度间隔不匹配

- 证据：[auto-update-service.ts](../local/src/lib/auto-update-service.ts:278) 逐个 `await` 处理全部订阅；每个源拉取可等 15 秒，[source-import.ts](../local/src/lib/source-import.ts:26)，带测活的单任务总上限为 3 分钟，[mihomo-health-check.ts](../local/src/lib/mihomo-health-check.ts:34)。Cron 运行期间其他触发仅返回 `already_running`，[update-subscriptions route](../local/app/api/cron/update-subscriptions/route.ts:24)；容器每 360 秒调用一次，[docker-compose.yml](../local/docker-compose.yml:45)。
- 影响：订阅数量稍增或单个源变慢时，后面的到期订阅会长期得不到处理。租约确保不会重复执行，但不会提供公平性、截止时间或待处理可见性。
- 最小修复：先把每次 Cron 的工作量限制到可完成的预算，并按 `lastAttemptedAt`/到期时间排序；记录未处理数量。若需要提高吞吐，先并行化纯网络拉取，mihomo 测活仍保持受控的独立队列，不要直接并行启动大量内核。

## 依赖处置

`npm audit --omit=dev` 共报告 6 个 high：`js-yaml`、`fast-uri`、`nanoid`、`deepmerge-ts` 及其 Prisma 影响链。`js-yaml` 是本报告确认会解析外部输入的生产风险，应优先升级。其余项中 `fast-uri` 与 `deepmerge-ts` 由 Prisma 工具链引入，升级前需在隔离分支验证 Prisma 7 与生成客户端；不要接受审计工具建议的 Prisma 大版本回退而不做迁移验证。

## 建议顺序

1. 先修复 DNS fail-open、下载更新 `updatedAt`、测活写回竞态，并分别添加回归测试。
2. 升级 `js-yaml` 和可安全升级的传递依赖，重新执行 `npm audit --omit=dev`。
3. 为规则请求补齐资源边界，再为 Cron 加工作预算和队列指标。
4. 若部署会扩容或暴露公网，在网关或共享存储上实现限流。
